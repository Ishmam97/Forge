## Problem

A developer running several coding-agent CLIs at once (Claude Code, Codex, OpenCode, Kimi, …) has no shared substrate for them to see each other's work or coordinate. Each CLI is a siloed session with its own context window, so **the human becomes the manual message bus** — copy-pasting state between terminals, relaying "task X is done, now start Y," and serializing work because parallel agents editing the same working tree clobber each other. There is no shared task board, no inter-agent messaging, no record of who is doing what or what it cost. The pain is acute precisely for the developer who has *already* adopted multiple agents to go faster: the coordination tax (context-shuttling, sequencing, conflict-avoidance) cancels much of the parallelism they were chasing.

## Target user

A **single developer on one machine, today, orchestrating 2–4 heterogeneous agent CLIs locally and supervising them** (the design's "topology A"). Concretely: a power user of terminal coding agents who already runs more than one vendor's CLI side-by-side (e.g. Claude Code as planner + Codex as implementer), is comfortable with `git worktree` and a local daemon, and feels the copy-paste relay tax daily. Not "every developer," and explicitly not (yet) teams, CI bots, or cross-machine fleets — though the core is designed so the *same substrate* later serves cross-machine agents (B), multiple humans (C), and autonomous swarms (D) without a rewrite.

## Jobs to be done

- **When** I have a feature that splits into two independent slices, **I want to** hand each slice to a different agent CLI and have them work at the same time without clobbering each other's files, **so I can** finish in roughly the wall-clock time of the slower slice instead of the sum of both.
- **When** one agent finishes a task that unblocks another, **I want to** have the handoff happen through a shared board the agents both read, **so I can** stop being the human relay that pastes "done — your turn" between terminals.
- **When** I'm supervising several agents at once, **I want to** watch a single live view of who claimed what, what's blocked, and what each task cost, **so I can** reassign or intervene without polling each terminal by hand.
- **When** I want to use the best (or cheapest, or least rate-limited) agent for a given role, **I want to** bind any MCP-capable CLI to Lead / Worker / Reviewer as config, **so I can** mix vendors freely instead of being locked to one orchestrator's agents.

## Value hypothesis

Today, coordinating N agents is an O(N) manual-attention cost on the human: every handoff, status check, and sequencing decision routes through copy-paste. We believe that giving the agents a shared, authoritative board + messaging + per-task worktree isolation collapses the **human-relay events per session toward zero on the happy path**, and converts two independent tasks from *sequential* (because of file clobbering and manual handoff) to *genuinely parallel*. The measurable bet: for a 2-task feature with orthogonal file sets, wall-clock-to-merge-ready drops meaningfully versus running the same two tasks through one agent sequentially, while the human's hands-on-keyboard coordination actions per task fall from "several" to "near zero" outside the human-gated merge approval. If that holds, the substrate pays for its setup cost the first time a developer runs two agents on one feature.

## Competitive landscape

This space moved fast in H1 2026; entries below are dated and cited. The sharpest comparison axis is the precise wedge: **local-first, heterogeneous *CLI coding agents*, sharing one authoritative board + per-task worktree isolation, coordinating over MCP, vendor-neutral, human-gated merge.** No single competitor occupies all of that; the closest (ReverbCode) overlaps heavily but differs on activation model and product shape.

**Direct / near-direct (shared board over MCP for heterogeneous CLI agents)**

- **BridgeMind** (BridgeMCP + BridgeSwarm + BridgeSpace) — the **closest comparator on the board-over-MCP axis**, and the one to study hardest. **BridgeMCP** is an MCP server exposing a *shared task board* (lifecycle `todo → in-progress → in-review → complete`) + shared knowledge (BridgeMemory knowledge graph) to **Cursor, Claude Code, Codex, Windsurf** and any MCP client — i.e. exactly our "heterogeneous CLI agents joining a shared board over MCP." **BridgeSwarm** layers roles (**Coordinator / Builder / Scout / Reviewer**) with **enforced file ownership** and a **quality gate before merge** — the same lead-and-delegate + human-gated-merge shape we propose. **BridgeSpace** is the supervisor UI: a Kanban board launching agents into **up to 16 parallel terminal sessions** with live output. **Does well:** essentially the whole conceptual surface — shared board, heterogeneous MCP clients, roles, pre-merge gate, live multi-terminal supervision. **What it misses relative to our wedge — and it's decisive:** BridgeMind is a **cloud-hosted SaaS** (paid tiers ~$16–$80/mo, credit-metered; BridgeSpace runs *cloud sandboxes*; project/task context flows to BridgeMind servers; account required). Our wedge is **local-first**: SQLite + a loopback daemon, no account, no subscription, code and coordination state never leave the machine. Secondary divergences: BridgeSwarm isolates via **file ownership** (the docs don't claim git-worktree isolation, which is our chosen primitive — orthogonal-or-sequential disjoint worktrees vs. ownership locks within one tree); and it's an integrated product/ecosystem (incl. its own BridgeCode CLI) rather than a thin neutral substrate. *Honest read: BridgeMind proves the board-over-MCP pattern is viable and being commercialized; our defensible difference is **local-first + zero-cloud + vendor-neutral substrate + worktree isolation**, not "a shared board exists." The PRD must answer "why not just use BridgeMind" with privacy/local-control + no-recurring-cost + worktree isolation, not novelty of concept.* Sources: [BridgeMCP](https://www.bridgemind.ai/bridgemcp), [BridgeSwarm](https://www.bridgemind.ai/bridgeswarm), [BridgeMind review (hosting/pricing), 2026](https://starsearn.com/guides/bridgemind-review-2026).

**Direct / near-direct (parallel CLI coding agents + worktrees)**

- **ReverbCode** (Go daemon + `ao` CLI + Electron supervisor; loopback HTTP, no auth/TLS by design). The closest thing that exists: supervises many coding-agent sessions, each in its own git worktree + terminal pane, and routes CI failures, review comments, and merge conflicts back to the owning agent. Claims **23 agent adapters** (claude-code, codex, cursor, opencode, aider, goose, copilot, kimi, …), so it is *already* heterogeneous and local-first. **Does well:** breadth of agent support, automated SCM-feedback routing, worktree-per-session, supervisor UI. **What it misses relative to our wedge:** its coordination unit is a *PR/SCM-feedback loop* and an external observer that **nudges** the owning agent — not a shared, agent-readable **task board** the agents claim from and message each other through; coordination is human-/PR-mediated rather than a first-class inter-agent board over MCP. It is also a heavier, opinionated product (Electron + zellij), not a thin MCP substrate other clients sit on. *Honest read: this is the incumbent to beat, and its existence is the strongest evidence both that the problem is real and that the design must articulate why a board+MCP substrate beats a supervisor+SCM-observer.* Notably, ReverbCode chose a **nudge/observe** activation model, not a held-open blocking poll — see Risks. Source: ReverbCode (AgentWrapper/agent-orchestrator) and the [Augment "9 open-source agent orchestrators" roundup](https://www.augmentcode.com/tools/open-source-agent-orchestrators).
- **ccswarm** — coordinates multiple agents in specialized pools inside worktree-isolated environments. **Does well:** worktree isolation + role pools, open-source. **Misses:** appears Claude-/single-stack oriented and pool-coordinated rather than a vendor-neutral board + MCP contract any CLI can join; less emphasis on a human live-dashboard. Source: [git-worktree AI tooling roundup, 2026](https://nimbalyst.com/blog/best-git-worktree-tools-ai-coding-2026/).
- **Augment Code "Intent"** (macOS) — dedicated branch+worktree per "space," specialist agents run in parallel in isolated dirs, a "Coordinator" sequences merges after verification. **Does well:** the worktree-per-task + verified-merge-sequencing model is almost identical to ours, with a polished native UX. **Misses:** vendor/product-bound (Augment's own agents, macOS app) — not a neutral substrate for arbitrary third-party CLIs over an open protocol; closed. Source: [Augment Code](https://www.augmentcode.com/guides/git-worktrees-parallel-ai-agent-execution).
- **Composio `agent-orchestrator`** — plans tasks, spawns agents, autonomously handles CI fixes, merge conflicts, code reviews. **Does well:** end-to-end autonomy incl. *automated* conflict handling. **Misses / diverges:** it bets on autonomous conflict resolution — exactly the thing our review *rejected* as unreliable for LLMs (we block + alert the human instead); and it's an orchestrator that spawns agents rather than a board heterogeneous human-launched CLIs voluntarily join. Source: [GitHub: ComposioHQ/agent-orchestrator](https://github.com/ComposioHQ/agent-orchestrator).
- **`gwq` / `agentree` / git-worktree-runner / worktree-cli** — worktree-creation utilities and status dashboards for AI workflows (some with MCP server integration). **Do well:** make per-agent worktrees frictionless; some expose MCP. **Miss:** they are *isolation plumbing*, not a coordination substrate — no shared board, no inter-agent messaging, no claim/lease/handoff semantics. They are complements our core could lean on, not competitors to the board. Source: [git-worktree tooling, 2026](https://nimbalyst.com/blog/best-git-worktree-tools-ai-coding-2026/).

**Adjacent: environment-isolation for parallel coding agents**

- **Dagger `container-use`** — an MCP server giving each agent its own *containerized* dev environment, each on its own git branch (worktree-backed), with full command-history visibility and "drop into the agent's terminal." **Does well:** strongest isolation (container + git, reproducible into CI), real visibility, already MCP-native and multi-agent. **Misses relative to our wedge:** it isolates *environments*, it is not a *coordination* layer — no shared task board, no inter-agent messaging, no lead/delegate or claim/lease semantics; agents work independently and report back, they don't collaborate through shared state. It's the best candidate for a future isolation backend *under* our board, not a substitute for it. Source: [Dagger blog](https://dagger.io/blog/agent-container-use/), [dagger/container-use](https://github.com/dagger/container-use).

**Multi-agent orchestration frameworks (library, not local CLI substrate)**

- **CrewAI / AutoGen (AG2) / LangGraph / OpenAI Agents SDK (ex-Swarm)** — frameworks for building multi-agent *applications* in code. CrewAI = role-based crews (closest in vocabulary: roles + delegation); LangGraph = stateful graph + durable checkpointing (most production-mature, built-in state persistence + time-travel); AutoGen = conversational GroupChat (Microsoft moved it to **maintenance mode** in favor of the Microsoft Agent Framework); OpenAI Agents SDK = lightweight handoffs. **Do well:** mature in-process orchestration, state management, large ecosystems. **Miss — categorically:** they orchestrate agents *you build inside one process/runtime*; they do **not** coordinate *independently-launched, heterogeneous vendor CLIs* each with its own context window, sharing one git repo with worktree isolation, joining voluntarily over MCP. Wrong altitude: they're how you'd *build* an agent, not how you'd let Claude Code and Codex (two separate products) share a board. Sources: [OpenAgents framework comparison, Feb 2026](https://openagents.org/blog/posts/2026-02-23-open-source-ai-agent-frameworks-compared), [Presenc AI 2026 roundup](https://presenc.ai/research/multi-agent-orchestration-frameworks-2026).

**Agent-interop protocols (substrate peers, not products)**

- **MCP** itself — our chosen transport for the agent↔core boundary. Handles the *vertical* model→tools connection. It is the right tool to *expose the board to agents*, but MCP alone is "an agent calls tools," not "a shared board + claims + leases + messaging + worktree mediation" — that coordination layer is exactly what we build on top.
- **Google A2A / Agent2Agent** (donated to the Linux Foundation; 150+ orgs, deep Google/Microsoft/AWS integration by early 2026) — standardizes *horizontal* agent-to-agent delegation/capability exchange. **Does well:** the emerging standard for agents to discover and delegate to each other at enterprise scale. **Misses relative to our wedge:** it's a *protocol for inter-agent messaging/delegation*, not a local-first product with a board, git-worktree mediation, and a human supervisor UI; it's aimed at networked enterprise agents, not a solo dev's local heterogeneous CLIs sharing one repo. Plausibly a *future* interop surface for topology B, not the MVP substrate. Sources: [A2A vs MCP](https://www.truefoundry.com/blog/mcp-vs-a2a), [A2A 1-year milestone, 2026](https://www.prnewswire.com/news-releases/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year-302737641.html).
- **IBM/Linux-Foundation ACP, ANP, Agora** — further interop standards (REST-native agent comms; decentralized agent networks/marketplaces). Same gap: protocols for networked agent communication, not a local board + worktree coordination product. Source: [agent protocol ecosystem map 2026](https://www.digitalapplied.com/blog/ai-agent-protocol-ecosystem-map-2026-mcp-a2a-acp-ucp).

**The vendor's own primitive**

- **Claude Code subagents + Task tool + Agent Teams** (Anthropic). Agent Teams (experimental) added a **shared task list** so subagents "coordinate through state, not back-and-forth messaging" — conceptually adjacent to our board. **Does well:** native, parallel subagents with isolated context; a shared-file-system task list. **Misses — exactly our wedge:** (1) it is **single-vendor** — subagents are all Claude, there is no Codex/OpenCode in the team; per the docs, "agents don't talk to each other directly… no message queue, no IPC," and "subagents… report results back in isolation… can't share findings or coordinate directly — when you need real collaboration, subagents hit a wall." (2) It coordinates through one harness's filesystem, not an authoritative cross-process daemon other vendors' CLIs can join. (3) Token cost is steep (≈20k overhead per Task; 3–4× tokens for active multi-agent sessions) and nesting is depth-limited. This is the single most important "why not just use the built-in" answer: **our differentiator is heterogeneous + cross-process + a real board with messaging and claims, where the native primitive is homogeneous, intra-harness, and report-back-only.** Source: [Claude Code Agent Teams deep dive](https://www.mindstudio.ai/blog/claude-code-agent-teams-parallel-shared-task-list), [Claude Code sub-agents docs/limits](https://code.claude.com/docs/en/sub-agents).

**Net gap this fills:** a **local-first, vendor-neutral coordination substrate** — an authoritative board + inter-agent messaging + claim/lease + core-mediated *git-worktree* isolation + human live-supervision — for **independently-launched, heterogeneous CLI coding agents** over MCP, with **no cloud, no account, no recurring cost, and code/state that never leaves the machine.** The concept is no longer novel — **BridgeMind** commercializes a strikingly similar board-over-MCP + roles + pre-merge-gate shape — so the defensible wedge has narrowed to three things competitors don't jointly offer: **(1) local-first / zero-cloud / privacy** (BridgeMind is hosted SaaS; the data leaves the machine), **(2) git-worktree isolation** as the parallelism primitive (BridgeMind uses file ownership; ReverbCode/container-use use worktrees/containers but aren't a neutral board), and **(3) a thin neutral substrate** other vendors' CLIs voluntarily join, rather than an integrated product or ecosystem. Frameworks are the wrong altitude (build-an-agent, not coordinate-CLIs); protocols are pieces not products; container-use/worktree tools isolate but don't coordinate; the native subagent primitive is single-vendor and report-back-only; ReverbCode coordinates via an SCM-observer that *nudges* agents rather than a board they claim from (and deliberately avoided the held-open blocking-poll activation this design bets on); and BridgeMind owns nearly the whole concept but only in the cloud.

## Success metrics

Leading indicators sized for a personal dev-tool MVP (instrument the daemon's event log; baseline = today's manual multi-terminal, single-or-sequential-agent workflow):

1. **Human-relay events per parallel session.** *Definition:* count of human actions that shuttle context/commands between agents (copy-paste of state, "now do Y" handoffs, manual worktree/path setup) on the happy path, excluding the one human-gated merge approval. **Baseline:** many (one per handoff + per status poll; realistically 6–12 for a 2-task feature). **Target:** ~0 on the happy path (handoffs flow through the board; merge approval is the only required human touch).
2. **Wall-clock to "both tasks merge-ready," parallel vs. sequential.** *Definition:* time from goal-decomposed to both disjoint tasks marked `merge_ready`, run on the substrate (2 agents in parallel) vs. the same two tasks through one agent sequentially. **Baseline:** ≈ sum of the two tasks' durations (sequential, plus relay overhead). **Target:** ≈ the slower single task's duration (within, say, 1.2×) — i.e. demonstrably sub-additive, proving real parallelism net of coordination overhead.
3. **Coordination reliability — % of tasks completing without a merge-conflict block, and % of tasks with token usage captured.** *Definition (a):* share of claimed tasks that reach `merge_ready` without tripping the conflict-block-and-alert path (validates that the Lead's orthogonal-file-set / sequential-dep discipline holds). *Definition (b):* share of tasks with a successful claim-time + done-time token checkpoint pair (validates the ledger schema). **Baseline:** n/a (no board today). **Target (MVP):** the 8-step vertical slice runs end-to-end with **0 unrecovered coordination failures** (every claim atomic, every lease honored, every status change reflected live), conflict-block path exercised at least once on purpose, and token usage captured on 100% of the slice's tasks. *Note:* token-checkpoint **accuracy** is explicitly not a metric this phase — capture-rate is (see token decision below).

(Headline MVP gate: the 8-step slice in the feature note completes with **zero human copy-paste of context or terminal commands** — metric #1 hitting ~0 is the proof.)

## Risks and unknowns

**Feasibility risk that could invalidate the core activation model (highest priority — researched):**

- **✅ Blocking long-poll activation — RESOLVED BY SPIKE (2026-06-26).** A probe MCP server and headless **Claude Code 2.1.193** and **Codex 0.142.0** clients completed held-open `block_for(130s)` calls cleanly with default settings and no progress notifications. Both agents parked on the call as instructed. The MVP adopts **configurable bounded long-poll**: the server returns work or an explicit empty result at a conservative bound, and the supported activation contract re-calls without human intervention. Architecture must specify cancellation, retry, and version-specific compatibility behavior, and the end-to-end suite must verify repeated handoffs rather than only one prompted wait. Method, limitations, and data: [`../learnings/2026-06-26-mcp-blocking-tool-call-activation.md`](../learnings/2026-06-26-mcp-blocking-tool-call-activation.md).
- **Will an arbitrary agent reliably "park" and resume on the next task?** Even if the transport tolerates a long/poll call, it's unproven that a general coding-agent CLI will *behaviorally* sit on `wait_for_my_next_task()` and then act on the returned task rather than ending its turn, summarizing, or asking the human. The activation contract may need per-agent prompt/profile scaffolding (fits the adapter model) — flag as part of the spike.

**Feasibility — agent-client maturity (researched, lower risk):**

- **Codex MCP-client maturity: looks adequate.** Codex CLI supports MCP servers over both **STDIO and Streamable HTTP**, configured in `~/.codex/config.toml` (or per-project `.codex/config.toml`) and managed via `codex mcp`, shared between CLI and IDE. So Codex-as-Worker connecting to the core's MCP adapter is plausible. **Unknown:** whether Codex honors the *same* timeout/keepalive semantics (ties directly to the blocking-poll risk) and how it behaves on long calls. Source: [Codex MCP docs](https://developers.openai.com/codex/mcp).
- **OpenCode / Kimi / other CLIs:** out of the MVP test matrix, but the agent-agnostic claim rests on their MCP-client maturity; ReverbCode listing adapters for them is encouraging but not a guarantee they tolerate this design's activation pattern. Validate per-agent as adapters are added.

**Product decisions and remaining architecture work:**

- **Working name** — unresolved; "AgentBus" remains the non-blocking codename. Candidates: WorktreeHub / RepoCrew / DevBoard / WorkBus.
- **Role→agent binding** — resolved for MVP: project configuration supplies initial vendor-neutral bindings and the human can override them through the UI.
- **Merge-conflict recovery** — resolved for MVP: the core blocks and alerts; the human resolves externally and requests a validated retry through the UI.
- **Heartbeat ↔ lease ↔ long-poll mechanics** — the product contract is resolved: idle waits hold no lease, active work uses explicit heartbeat calls, clean expired worktrees requeue automatically, and dirty expired worktrees block for human reassignment. Architecture must define fencing and transaction details.
- **Token checkpoints** — resolved for MVP: self-reported checkpoints prove schema and capture rate only. Accurate telemetry remains out of scope.

**Strategic risk:**

- **Incumbent overlap (BridgeMind, ReverbCode, Augment Intent).** The concept is already commercialized. **BridgeMind** is the sharpest threat: its BridgeMCP + BridgeSwarm + BridgeSpace stack delivers nearly our entire conceptual surface (shared board over MCP for Claude Code/Codex/Cursor/Windsurf, Coordinator/Builder/Reviewer roles, pre-merge gate, live multi-terminal supervision) — but as **cloud SaaS** with metered pricing. ReverbCode covers the local + broad-adapter + worktree angle via an SCM-observer-nudge model. **Implication:** "a shared board for heterogeneous agents" is no longer a differentiator on its own. The wedge must rest on **local-first / zero-cloud / privacy + git-worktree isolation + thin neutral substrate**, and that must translate into a *felt* advantage (no recurring cost, code never leaves the machine, works fully offline). The PRD needs explicit "why not just use BridgeMind" and "why not just use ReverbCode" answers; without a crisp one, the MVP risks being a thinner, local re-implementation of an existing product.

## Non-goals

- Cross-machine, multi-user, auth/access control (topologies B/C) — *design for, don't build.*
- Fully autonomous, human-out-of-the-loop swarm (D).
- **Autonomous LLM merge-conflict resolution** — deliberately rejected; conflicts block and alert the human (this is where we diverge from Composio's orchestrator).
- Accurate cross-agent token telemetry and token-optimized auto-routing — schema only this phase; no routing/budgeting logic.
- Concurrent editing of one working tree — structurally avoided by worktree-per-task.
- A full drag-and-drop Kanban UI — thin live dashboard + basic reassign actions only.
- OpenCode / Kimi / other agents in the MVP **test matrix** — architecture supports them; proving set is Claude Code (Lead) + Codex (Worker) only. (Test-surface limit, *not* an architectural one — the design stays role-pluggable.)
- A "get full board" tool — context bloat; granular `get_my_assigned_tasks` / `get_task_context(id)` only.
- Auto-spawning the daemon via lockfiles/sockets — explicit `agentbus serve` for v1.
